## 关键发现

### v1.3 修复记录

#### TC-HANDLE-IDEMPOTENT 协同任务 handle 重复点击幂等

- **背景**: 销售/运营在 `status=handled` 后再次点击 handle 按钮（前端未及时 disable / 弱网重试），后端返 422 `cannot handle task in status handled`，影响体验。
- **修复前**: `backend/src/modules/collaboration-tasks/collaboration-tasks.service.ts:305-307` 在 `task.status !== 'handling' && task.status !== 'pending'` 时一律抛错，已 handled 任务的所有 handle 调用都被拒。
- **修复后**（最小化改动，仅 service + controller 错误码翻译）:
  - `collaboration-tasks.service.ts:305-328` 增加幂等短路：已 handled 任务若当前用户是 task.handlerId / admin / owner / supervisor → 直接返回 `{ ...task, alreadyHandled:true, handledBy, handledAtField }`，不再走 status 校验 / repo.update / 通知副作用。
  - 其它角色（销售 A 重复 handle 运营已 handled 的任务）继续走 `assertCanHandle` 抛 `no permission to handle task`；controller 翻译为 403，与 close 路径一致。
  - `collaboration-tasks.controller.ts:193-201` runHandle 的 catch 中按 msg 区分 403（no permission / handler required）vs 422（其它业务错误）。
- **不变量保证**:
  - 真的非法状态（closed / timeout）仍走原 `cannot handle task in status ...` 抛 422；
  - 非处理人重复 handle 仍 403，不泄漏 handledNote / handlerId / handledAt 给非授权人；
  - 通知 / lead 状态回写 / operation_logs 仅在 status 真正 pending→handled 转换时触发，幂等路径不重复发通知、不重复改 lead。
- **验证场景**:
  - 同 handler 重复 handle：200 + `task.status=handled, alreadyHandled=true`
  - 新任务（status=pending）正常 handle：200 + `task.status=handled, alreadyHandled` 字段不存在
  - status=closed 的 handle：仍 422 'cannot handle task in status closed'
  - 非处理人重复 handle：403 'no permission to handle task'

### 严重问题 (P0)

#### 1. 后端未实现 `sort=traffic` 排序逻辑
- **影响用例**: OP-21-010
- **位置**: `backend/src/modules/posts/posts.service.ts:79-91`
- **描述**: 只有 `sort=leads` 有专门的子查询排序处理，`sort=traffic` 走默认 `publishedAt DESC` 排序。前端使用客户端排序兜底，但在大分页场景（如 page=5, pageSize=50=250条）下客户端排序覆盖有限（仅当前页数据）
- **代码证据**: `posts.service.ts` 第 79-91 行 `if (filters.sort === 'leads') { ... } else { 默认排序 }`
- **修复建议**: 在 `posts.service.ts:findPaged` 中为 `sort=traffic` 增加 `qb.orderBy('p.traffic', 'DESC')` 分支

#### 2. 主管回复/转发提醒功能未实现
- **影响用例**: SUP-3-006, SUP-3-007
- **描述**: 主管收到提醒后，无法通过 API 回复或转发。通知系统是单向的（内部创建→主管接收），没有双向交互
- **修复建议**: 添加 `POST /api/reminders/:id/reply` 和 `POST /api/reminders/:id/forward` 端点

#### 3. 员工选择器状态未持久化
- **影响用例**: SUP-2-024
- **位置**: `frontend/src/app/admin/personal/page.tsx`
- **描述**: 员工选择器切换到不同员工后，刷新页面或切换 tab 后丢失选择状态
- **修复建议**: 将 `selectedEmployeeId` 写入 URL searchParams 或 localStorage

#### 4. URL 状态同步缺失
- **影响用例**: OP-21-017
- **位置**: `frontend/src/app/admin/posts/page.tsx`
- **描述**: 筛选条件和排序状态不更新 URL，导致无法分享当前视图
- **修复建议**: 使用 `useSearchParams` 或 `useEffect` 同步 filters/sort 到 URL

### 一般问题 (P1)

#### 5. 效率榜进度条样式识别性问题
