| 项目 | 说明 |
| --- | --- |

# 一、系统总体定位与最终交付边界
**系统定位：**本系统是公司内部的运营协同中台，不是单纯的发帖记录工具，也不是传统销售CRM。它要把运营作品、客资来源、销售跟进、教务订单跟进和主管管理打通，形成一套可持续使用的内部工作系统。
**最终交付边界：**系统最终只划分四个端口：运营端、销售端、教务端、主管端。系统配置、员工管理、账号管理等后台能力归入主管端的管理权限，不再单独作为第五端口。
**核心链路：**账号和作品产生客资，运营录入并分配销售，销售跟进客户并触发运营协同，成交后进入订单和教务跟进，主管查看团队数据、个人看板和整体进度。

| 端口 | 核心使用人 | 主要目标 | 关键页面 |
| --- | --- | --- | --- |
| 运营端 | 运营员工 | 发作品、录客资、看排行、学习优秀作品、查看自己的作品和客资。 | 今日任务、运营排行榜、学习榜单、作品广场、个人看板、作品录入、客资录入、客资看板、我的作品、账号管理 |
| 销售端 | 销售人员 | 接收分配客资、跟进添加状态、发起运营协同、推进成交、管理订单跟进。 | 我的客资、待跟进、协同申请、跟进记录、订单跟进、消息提醒 |
| 教务端 | 教务/交付人员 | 接收成交订单，跟进交付进度、提醒节点、反馈异常。 | 订单池、订单详情、进度跟进、节点提醒、异常提醒、交付记录 |
| 主管端 | 运营主管/管理者 | 看整体、看个人、管员工、管账号、看作品与客资、导出数据。 | 总览、个人看板选择器、运营排行榜、作品看板、客资看板、员工管理、账号管理、基础分析看板 |


# 二、产品与交互设计总原则
- 四端口必须使用同一套数据底座，但页面和权限必须分开。运营只看到自己相关内容，销售只看到分配给自己的客资，教务只看到进入订单交付的客户，主管可以全局查看。
- 所有列表型页面必须支持筛选、搜索、分页、排序和Excel导出。数据量变大后不能一次性加载全部数据。
- 所有高频操作必须少填字段。作品录入尽量只填链接或上传截图；客资录入尽量通过粘贴内容、截图、手机号、微信号等信息自动带出可识别字段。
- 所有跨端协作必须有明确状态和消息提醒。不能只靠人工口头通知。
- 界面必须CRM化：左侧导航、顶部状态、主体卡片和表格，不做过多花哨图表，不堆叠无意义颜色。
- 主管端重点是管理效率，运营端重点是使用方便和竞争激励，销售端重点是跟进闭环，教务端重点是订单节点不遗漏。
# 三、角色权限与数据可见范围

| 角色 | 可查看数据 | 可操作数据 | 不可查看/不可操作 |
| --- | --- | --- | --- |
| 运营员工 | 自己的作品、自己的客资、自己账号、运营排行榜、学习榜单、作品广场中允许公开的作品。 | 录入作品、录入客资、编辑自己的作品和客资、响应销售协同、更新自己账号人设和发帖规划。 | 其他运营的私密客资、销售跟进详情、订单金额和教务交付细节。 |
| 销售人员 | 分配给自己的客资、自己的跟进记录、与自己相关的协同任务、自己负责的订单。 | 更新客资添加状态、跟进状态、成交状态，发起运营协同，填写跟进记录。 | 未分配给自己的客资、运营全部账号数据、其他销售跟进详情。 |
| 教务人员 | 已成交/已进入交付的订单、客户基础需求、交付节点、老师或专家安排信息。 | 更新订单进度、添加教务提醒、登记交付动作、反馈异常。 | 未成交客资、销售私密沟通、运营全部原始内容数据。 |
| 主管 | 全局作品、客资、员工、账号、排行榜、协同任务、销售分配和教务订单汇总。 | 管理员工、账号、权限、分配规则、导出数据、查看任一员工个人看板。 | 无。 |
| 系统管理员权限 | 同主管。 | 系统配置、字段配置、数据字典、备份恢复、日志查看。 | 该权限不单独作为端口，只作为主管端高级权限。 |


# 四、运营端最终功能说明
运营端的核心不是“管理”，而是让运营每天愿意用、录得快、看得到差距、学得到优秀作品。运营端必须强化竞争感、反馈感和学习感。
## 4.1 运营端导航结构

| 一级菜单 | 页面目标 | 必须保留/新增功能 |
| --- | --- | --- |
| 今日任务 | 让运营知道今天该做什么、还差什么。 | 今日作品数、今日客资数、今日待处理协同、未完成录入、主管提醒。 |
| 运营排行榜 | 通过公开排名形成相互竞争和督促。 | 作品数榜单、客资榜单、流量榜单、学习榜单入口。 |
| 个人看板 | 运营查看自己本月/本周表现、账号表现和效率。 | 获客数榜、获客效率榜、获客贴效率榜、流量榜、非获客贴数榜。 |
| 作品录入 | 最少操作提交作品。 | 链接识别、截图上传、封面上传、自动提取基础信息、手动兜底。 |
| 客资录入 | 最少操作提交客资并支持分配销售。 | 粘贴文本解析、截图上传、来源作品选择、销售分配、联系方式字段校验。 |
| 客资看板 | 查看自己录入的客资和协同状态。 | 只看自己的客资；显示销售是否申请、客户是否通过、运营是否已提醒。 |
| 我的作品 | 查看自己全部作品和主管建议。 | 筛选、编辑、打开原帖、查看数据、查看主管建议。 |
| 作品广场 | 看其他人的作品，学习标题、文案、类型和获客效果。 | 按平台、类型、获客数、点赞数、员工筛选；敏感字段隐藏。 |
| 账号管理 | 维护自己负责账号的人设、定位和发帖规划。 | 账号列表、账号状态、人设、定位、发帖规划、主管建议。 |


## 4.2 运营排行榜
运营排行榜必须成为运营端的核心页面，突出竞争感。页面默认按本周展示，可切换今日、本周、本月、累计。榜单数据要统一口径，避免员工质疑排名不公平。

| 榜单 | 计算口径 | 展示内容 | 交互要求 |
| --- | --- | --- | --- |
| 作品数榜单 | 统计周期内员工录入且审核有效的作品总数。删除、重复、无效作品不计入。 | 排名、员工姓名、作品数、小红书作品数、抖音作品数、与上一名差距。 | 支持今日/本周/本月/累计切换；点击员工可进入该员工公开作品列表。 |
| 客资榜单 | 统计周期内员工录入且有效的客资数。重复客资、无联系方式且不可跟进的客资不计入有效客资。 | 排名、员工姓名、客资数、来源作品数、有效率、与上一名差距。 | 强调“距离上一名差多少”，形成追赶感。 |
| 流量榜单 | 统计周期内员工名下作品总点赞数排名。当前版本流量只按点赞数计算，不用播放量。 | 排名、员工姓名、点赞数、作品数、平均点赞、最高点赞作品。 | 点击最高点赞作品可打开作品详情。 |
| 学习榜单 | 汇总近期获客效果最好的前5-10个账号和作品。排序以客资数优先，客资相同再看获客效率和点赞数。 | 优秀账号、优秀作品标题、平台、作品类型、客资数、点赞数、所属员工、可学习点。 | 不强调竞争，强调复盘学习。允许主管填写“为什么值得学”。 |


## 4.3 学习榜单详细要求
- 学习榜单必须同时支持“优秀账号榜”和“优秀作品榜”。默认展示近7天，可切换近14天、近30天。
- 优秀账号榜取前5-10名，字段包括账号名、平台、所属运营、发帖数、客资数、平均客资/作品、最高获客作品。
- 优秀作品榜取前5-10条，字段包括封面、标题、文案摘要、平台、作品类型、点赞数、评论数、收藏数、转发数、客资数、所属账号、所属运营。
- 学习榜单要支持“打开原帖”“查看同类作品”“收藏学习”“主管点评”。主管点评是人工输入，不做AI分析。
- 作品广场和学习榜单中的客资联系方式、客户昵称、销售跟进等敏感信息必须隐藏，只展示作品层面的结果数据。
## 4.4 个人看板优化
个人看板要让运营快速知道自己的账号结构、作品结构、获客能力和流量能力。当前已有获客数榜、效率榜、获客贴效率榜，需要新增流量榜和非获客贴数榜。

| 模块 | 展示内容 | 说明 |
| --- | --- | --- |
| 个人概览 | 本月作品数、本月客资数、本月点赞数、有效账号数、获客贴数、非获客贴数。 | 顶部用少量卡片展示，不要堆过多指标。 |
| 获客数榜 | 按账号统计客资数排名。 | 看哪个账号带客资最多。 |
| 获客效率榜 | 客资数 / 作品数。 | 看哪个账号单位作品获客能力强。 |
| 获客贴效率榜 | 客资数 / 获客贴数。 | 看获客型内容是否有效。 |
| 流量榜 | 按账号或作品点赞数排名。 | 当前流量榜统一以点赞数为主，不引入播放量。 |
| 非获客贴数榜 | 按账号统计非获客贴数量。 | 用于判断账号是否在养号、铺内容、做信任，不只看获客贴。 |
| 账号日历 | 按日期展示每个账号是否发帖、发了几条、类型是什么。 | 方便员工回看漏发和账号节奏。 |


## 4.5 作品广场
作品广场的目的不是管理，而是让运营互相学习。运营可以看到其他人的公开作品，但不能看到客户隐私和销售转化信息。

| 功能 | 要求 |
| --- | --- |
| 筛选 | 平台、作品类型、员工、账号、时间、点赞数区间、客资数区间。 |
| 排序 | 按发布时间、点赞数、客资数、获客效率排序。 |
| 展示字段 | 封面、标题、文案摘要、平台、账号、作品类型、点赞/评论/收藏/转发、客资数、发布时间。 |
| 操作 | 打开原帖、复制参考链接、收藏学习、查看同账号作品。 |
| 权限 | 不展示客户联系方式、不展示销售分配、不展示成交信息。 |


## 4.6 作品录入
作品录入必须足够简单，优先支持“粘贴链接自动带出内容”。如果平台限制导致无法自动抓取，则支持手动兜底。

| 录入方式 | 系统动作 | 运营需要补充 |
| --- | --- | --- |
| 粘贴作品链接 | 自动识别平台、账号、标题、封面、发布时间、点赞数、评论数、收藏数、转发数、文案。 | 作品类型、是否获客贴、备注。 |
| 上传截图/封面 | 保存图片并关联作品，允许后续主管和员工查看。 | 标题、文案、平台、账号、类型。 |
| 手动录入 | 作为兜底方案，保存完整字段。 | 全部必要字段。 |


- 系统必须做链接去重，同一个作品链接不能重复录入。
- 作品指标允许后续更新，不能因为当天录入数据为0就锁死。
- 录入成功后立即进入“今日录入记录”和“我的作品”，主管端同步可见。
- 作品类型至少包括：素人贴、话题贴、获客贴、非获客贴。具体类型可以在主管端配置。
## 4.7 客资录入
客资录入要服务于后续销售跟进，因此必须保证联系方式、来源作品、来源平台、所属运营、分配销售、状态都能被准确保存。

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 来源账号 | 必填 | 客资来自哪个运营账号。 |
| 来源作品 | 建议必填 | 尽量关联具体作品；没有作品时可选择“无来源作品/私信自然客资”。 |
| 平台 | 必填 | 小红书、抖音等。 |
| 昵称 | 选填 | 客户平台昵称。 |
| 联系方式 | 必填 | 微信、手机号或其他可联系信息。至少一个可跟进联系方式。 |
| IP/地区 | 选填 | 用于判断客户地域。 |
| 需求备注 | 选填 | 客户咨询内容、专业、预算、周期等。 |
| 分配销售 | 选填/可后补 | 运营录入时可直接分配销售；未分配则进入待分配状态。 |
| 客资状态 | 系统生成 | 新客资、已分配、销售跟进中、协同中、已通过、已成交、无效等。 |


- 支持粘贴聊天内容自动分段放入备注区，系统自动识别手机号、微信号等明显字段。
- 支持上传引流截图，截图必须与客资记录绑定。
- 提交后销售端是否弹提醒，取决于是否已经分配销售。
- 客资录入页面下方必须显示今日录入记录，便于运营当天回查和修改。
# 五、主管端最终功能说明
主管端不需要把所有细节堆在首页。主管端的核心是快速看整体、看异常、看个人、看作品、看客资。个人看板不需要重新做复杂页面，只需要选择某个员工后，查看该员工与运营端一致的个人看板。
## 5.1 主管端导航结构

| 一级菜单 | 页面目标 | 功能要求 |
| --- | --- | --- |
| 总览 | 查看团队当天和周期总体情况。 | 作品数、客资数、点赞数、有效账号数、待处理协同、风险提醒。 |
| 运营排行榜 | 查看全员排名和学习榜单。 | 作品数榜、客资榜、流量榜、学习榜。 |
| 个人看板 | 选择任一员工查看其个人看板。 | 员工选择器 + 与运营端相同的个人看板。主管可查看全部员工。 |
| 作品看板 | 直观查看全公司作品。 | 卡片/列表结合，支持平台、员工、账号、类型、时间、数据排序。 |
| 客资看板 | 直观查看全公司客资和协同状态。 | 按员工、销售、平台、状态、日期筛选；支持导出。 |
| 员工管理 | 管理员工和登录账号。 | 新增、停用、角色、所属端口、登录账号、账号分配。 |
| 账号管理 | 管理运营账号。 | 账号平台、所属员工、人设、定位、状态、发帖规划。 |
| 分析看板 | 保留基础分析能力，后续再细化。 | 先保留平台趋势、作品结构、客资趋势，不做复杂扩展。 |


## 5.2 主管端个人看板
- 主管端个人看板顶部必须有员工选择器，选择员工后展示该员工个人看板。
- 页面不需要主管重新录入数据，也不需要重新拆一套指标，直接复用运营端个人看板口径。
- 主管可以查看该员工的账号日历、获客数榜、获客效率榜、获客贴效率榜、流量榜、非获客贴数榜。
- 主管可以在个人看板中对某个账号或作品添加“主管建议”，该建议同步给员工端。
## 5.3 主管端作品看板

| 区域 | 要求 |
| --- | --- |
| 顶部筛选区 | 时间、平台、员工、账号、作品类型、是否获客贴、点赞排序、客资排序。 |
| 作品列表 | 封面、标题、文案摘要、平台、账号、所属员工、发布时间、作品类型、点赞/评论/收藏/转发、客资数。 |
| 主管操作 | 打开原帖、查看详情、填写主管建议、标记优秀作品、导出当前筛选结果。 |
| 详情弹窗 | 展示完整文案、截图、数据、来源客资列表、主管建议历史。 |
| 性能要求 | 分页加载，每页20条或50条，不允许一次渲染几百条作品卡片。 |


## 5.4 主管端客资看板

| 区域 | 要求 |
| --- | --- |
| 顶部筛选区 | 日期、平台、所属运营、分配销售、来源账号、来源作品、处理状态、添加状态、成交状态。 |
| 数据统计卡 | 筛选范围客资数、新客资、已分配、待添加、已通过、协同中、已成交、无效。 |
| 客资卡片/表格 | 客户昵称/联系方式脱敏、来源平台、来源账号、来源作品、所属运营、分配销售、处理状态、添加状态、协同状态、最后更新时间。 |
| 主管操作 | 分配/改派销售、提醒运营、提醒销售、查看跟进记录、导出Excel。 |
| 视觉要求 | 状态标签必须清晰：未分配、已分配、待添加、未通过、已提醒、已通过、已成交、无效。 |


# 六、销售端最终功能说明
销售端只围绕三件事：查看分配给自己的客资、推进客资添加与跟进、跟进成交后的订单。销售端不需要看到复杂运营数据。

| 菜单 | 目标 | 功能要求 |
| --- | --- | --- |
| 我的客资 | 查看分配给自己的全部客资。 | 按新客资、待添加、未通过、已通过、跟进中、已成交、无效筛选。 |
| 待跟进 | 处理今日必须跟进的客户。 | 自动显示新分配、超时未跟进、未通过待处理、已通过待沟通。 |
| 客资详情 | 完整记录销售动作。 | 查看来源、联系方式、截图、运营备注、跟进记录、协同记录。 |
| 协同申请 | 向运营发起协同。 | 申请客户提醒、补充来源信息、确认客户身份、请求运营二次触达。 |
| 订单跟进 | 对已成交客户进行订单状态跟进。 | 成交金额、产品类型、合同/付款状态、交接教务状态、后续节点。 |
| 消息中心 | 接收运营和主管提醒。 | 新分配客资、运营已处理、客户已通过、主管提醒、教务反馈。 |


## 6.1 销售客资卡片字段

# 七、教务端最终功能说明
教务端负责成交后的订单交付跟进与提醒。教务端不是销售CRM，也不是运营系统，只需要围绕订单交付进度、节点提醒和异常反馈。

| 菜单 | 目标 | 功能要求 |
| --- | --- | --- |
| 订单池 | 查看进入教务的全部订单。 | 按待接收、进行中、待客户资料、待老师安排、待交付、已完成、异常筛选。 |
| 订单详情 | 查看客户需求和销售交接信息。 | 客户基础信息、服务类型、成交信息、交付要求、资料情况、备注。 |
| 进度跟进 | 记录教务处理动作。 | 每次沟通、资料收集、老师安排、节点完成都要留痕。 |
| 节点提醒 | 防止订单忘记推进。 | 按订单节点生成提醒，例如资料未收齐、老师未安排、客户未回复、交付即将到期。 |
| 异常反馈 | 把交付异常同步给销售或主管。 | 客户不配合、资料缺失、老师未响应、周期风险等。 |
| 导出 | 导出订单列表和交付进度。 | 支持按时间、状态、销售、教务导出Excel。 |


# 八、客资协同状态机与跨端提醒规则
客资协同是本系统最重要的闭环。必须把运营、销售之间的动作变成状态，而不是只显示一条备注。
## 8.1 客资主状态

| 状态 | 触发条件 | 可操作角色 | 下一步 |
| --- | --- | --- | --- |
| 新客资 | 运营录入客资但未分配销售。 | 运营、主管 | 分配销售或补充信息。 |
| 已分配销售 | 运营或主管选择销售后。 | 销售、主管 | 销售收到弹窗提醒，开始添加客户。 |
| 销售跟进中 | 销售查看或填写首次跟进记录。 | 销售 | 更新添加状态或申请运营协同。 |
| 申请运营协同 | 销售点击申请协同。 | 销售、运营 | 运营收到提醒，在客资卡片处理。 |
| 运营处理中 | 运营确认收到并开始处理。 | 运营 | 标记已提醒客户或补充信息。 |
| 运营已处理 | 运营完成提醒客户/补充信息/二次触达。 | 运营、销售 | 销售收到通知继续跟进。 |
| 已添加通过 | 销售确认客户已通过好友。 | 销售、运营 | 运营收到通知，客资进入销售跟进。 |
| 已成交 | 销售标记成交并填写成交信息。 | 销售、教务、主管 | 同步到教务端订单池。 |
| 无效客资 | 销售或主管确认无法跟进。 | 销售、主管 | 保留记录，不进入后续跟进。 |


## 8.2 添加状态

| 添加状态 | 说明 | 提醒规则 |
| --- | --- | --- |
| 未添加 | 销售尚未添加客户。 | 新分配后销售端红点提醒。 |
| 已申请添加 | 销售已尝试添加客户。 | 记录时间，超过设定时间未通过可提醒。 |
| 客户未通过 | 客户未通过好友或未响应。 | 销售可提醒运营，运营端收到“客户待提醒”。 |
| 运营已提醒客户 | 运营完成对客户的提醒动作。 | 销售端收到“运营已处理”通知。 |
| 已添加通过 | 客户通过好友。 | 运营端收到“销售已添加通过”通知。 |


## 8.3 关键协同场景

| 场景 | 流程 | 系统必须实现 |
| --- | --- | --- |
| 运营上传并分配销售 | 运营录入客资 -> 选择销售 -> 提交。 | 销售端实时弹窗；销售消息中心新增未读；客资进入销售“新分配”。 |
| 销售申请运营协同 | 销售在客资卡片点击申请协同 -> 填写原因。 | 运营端该客资卡片显示“销售已申请”；运营消息中心产生提醒；主管端可看到协同状态。 |
| 客户未通过 | 销售标记客户未通过 -> 选择“提醒运营处理”。 | 运营端收到客户待提醒；客资卡片出现处理按钮；销售端显示“待运营处理”。 |
| 运营未处理 | 超过设定时间仍未标记已处理。 | 系统提醒运营；销售端可以再次提醒；主管端显示协同超时。 |
| 运营已处理 | 运营点击“已提醒客户”并填写备注。 | 销售端收到通知；状态变为“运营已处理”；保留处理记录。 |
| 销售添加成功 | 销售点击“已添加通过”。 | 运营端收到通知；主管端状态同步；客资进入销售跟进中。 |
| 成交进入教务 | 销售标记成交并填写订单信息。 | 教务端订单池新增订单；教务收到提醒；主管端能看到成交与交付状态。 |


## 8.4 消息提醒分类

| 提醒类型 | 接收端 | 触发事件 | 呈现方式 |
| --- | --- | --- | --- |
| 销售提醒 | 销售端 | 新分配客资、运营已处理、客户来源信息更新、主管提醒。 | 红点、弹窗、消息中心。 |
| 运营提醒 | 运营端 | 销售申请协同、客户未通过需提醒、销售添加成功、主管建议。 | 红点、客资卡片标签、消息中心。 |
| 主管提醒 | 主管端 | 协同超时、员工低更新、客资积压、账号异常。 | 主管消息中心和总览提醒。 |
| 教务提醒 | 教务端 | 新成交订单、资料未收齐、节点到期、异常反馈。 | 红点、订单卡片标签、消息中心。 |

# 十一、并发、性能与稳定性要求
系统设计必须按未来扩张考虑，而不是只满足当前人数。当前运营约12人，销售5-6人，教务若干，主管1人；后续运营和销售都会增长。系统至少按50-100人同时在线设计。

| 使用场景 | 并发特点 | 性能要求 |
| --- | --- | --- |
| 运营集中录入作品 | 运营在同一时间段上传截图、粘贴链接、提交作品。 | 上传接口异步处理；图片走对象存储；提交后立即返回；后台再补充抓取指标。 |
| 运营集中录入客资 | 大量客资在同一天集中录入，同时可能分配销售。 | 客资创建必须事务化，确保客资、附件、通知同时成功或回滚。 |
| 销售集中处理客资 | 销售同时打开客资列表、更新状态、填写跟进。 | 列表分页；状态更新加乐观锁，避免覆盖。 |
| 主管查看看板 | 主管按日期、员工、平台筛选大量数据。 | 统计数据使用缓存和预聚合，不直接实时扫全表。 |
| 消息实时推送 | 多个端口同时接收提醒。 | 使用Socket.IO + Redis适配器，通知同时入库，离线后可补看。 |
| Excel导出 | 主管或员工导出较大数据。 | 必须后端异步导出，生成文件后通知下载，禁止前端一次性拉全量生成。 |


## 11.1 技术架构建议

| 层级 | 建议方案 | 说明 |
| --- | --- | --- |
| 前端 | React / Next.js + Ant Design Pro | 适合CRM后台风格，四端口可复用组件。 |
| 后端 | NestJS / Node.js | 模块化清晰，适合权限、消息、接口和业务服务拆分。 |
| 数据库 | MySQL 或 PostgreSQL | 保存核心业务数据。 |
| 缓存 | Redis | 排行榜、看板统计、消息未读数、导出任务状态。 |
| 实时通信 | Socket.IO | 跨端实时提醒。 |
| 文件存储 | OSS / MinIO / S3 | 保存封面、截图、附件。不要长期存本地uploads。 |
| 队列 | BullMQ / Redis Queue | 链接解析、指标抓取、Excel导出、提醒重试。 |
| 部署 | Docker + Nginx + PM2 或进程管理器 | 保证服务稳定、便于重启和迁移。 |

- 导出必须保留当前筛选条件，用户看到什么范围，就导出什么范围。
- 导出任务要写入 exports 表，便于追踪谁在什么时候导出了什么数据。
- 涉及手机号、微信号等敏感信息时，普通员工默认脱敏；主管权限可导出完整字段。
# 十三、界面与易用性细节要求
- 四端口保持统一视觉：左侧导航、顶部状态栏、主体卡片、表格和筛选区。
- 重要状态必须用标签展示，例如“待销售添加”“客户未通过”“待运营处理”“运营已处理”“已添加通过”“已成交”。
- 表单字段要减少必填项。确实不确定的信息允许后补，但联系方式、来源平台、所属运营必须明确。
- 所有高频页面顶部必须有快捷筛选：今天、本周、本月、累计。
- 客资卡片必须把“下一步该谁处理”显示清楚，避免运营和销售互相等。
- 主管端作品看板和客资看板必须优先保证直观，不要为了展示所有信息把卡片做得过宽过乱。
- 分析看板当前只保留基础数据，不做复杂扩展，后续等业务口径明确后再优化。

# 十五、开发落地注意事项
- 开发时不要先做复杂分析看板，先把四端口主流程、排行榜、客资协同、订单跟进和导出做扎实。

- 所有提醒必须既实时推送，也要入库保存，避免用户离线后丢消息。
- 所有列表都要分页，所有大文件都要对象存储，所有导出都要后端异步。
- 主管端和运营端的个人看板要共用同一套统计接口，只是权限范围不同。
- 学习榜单和作品广场要隐藏客户隐私，只展示作品层面的数据和学习信息。

# 十七、教务端新架构实现说明

> 背景：教务端不在 v1 原型基础上迁移或兼容，而是在新的前后端代码基础上重新实现。v1 原型（参见第十六章）作为业务参考，不参与新版本构建。

## 17.1 实现目标

- 在新架构下完整实现 v1 原型已验证的全部业务能力
- 与运营端、销售端、主管端形成统一数据底座、权限体系和提醒体系
- 支持多人并发操作、主管端全局查看、销售端成交后订单可见
- 补齐 v1 原型缺失的能力：后端数据库、正式权限隔离、消息提醒自动化、附件云端存储、登记表单解析、Excel 导出

## 17.2 技术栈选型

| 层级 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | 统一前端栈（React / Next.js） | 与四端口共用组件、布局、设计系统 |
| 后端 | NestJS（`backend/` 目录）作为业务模块 + Node.js/Express 单体作为宿主 | 沿用 `server.js` 入口，按模块拆出 orders/teachers/reminders 等子服务 |
| 数据库 | MySQL | 沿用 `schema.sql`，按 17.4 扩展教务端相关表 |
| 缓存 | Redis | 教务端待办、节点提醒、消息未读数 |
| 实时通信 | Socket.IO | 复用 `lead.assigned` / `order.created` / `order.updated` / `notification.created` 事件 |
| 文件存储 | OSS / MinIO / S3 | 替代 v1 原型的本地附件存储 |
| 导出 | 后端异步 + `exports` 表 | 沿用第十二章导出规范 |

## 17.3 v1 业务能力映射

| v1 原型能力 | 新架构落地方式 |

## 17.6 集成点

- 与销售端：销售标记成交 → `order.created` 事件 → 教务端订单池新增；销售可在订单跟进页查看进度。
- 与运营端：运营作品与客资与订单通过 `leads.lead_id` 关联，但教务端不直接读取运营私密数据。
- 与主管端：主管端总览接入教务端订单汇总、风险订单、节点超时；主管端可下钻到订单详情。
- 与通知中心：节点提醒、异常反馈、超时订单走 `notifications` 表 + `notification.created` 实时事件。
