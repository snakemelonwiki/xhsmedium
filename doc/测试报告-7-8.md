# #7 批量导入 - 代码核对报告

| 序号 | 需求项 | 判定 | 证据/缺失说明 |
|---|---|---|---|
| 1 | 作品和客资均支持单条录入、批量粘贴录入、Excel模板导入 | ⚠️ 部分满足 | 作品：单条录入 ✅（PostsController.create）、批量粘贴 ✅（imports/posts/paste）、Excel导入 ❌（无实现）。客资：单条录入 ❌（前端无入口）、批量粘贴 ✅（leads/import-paste 后端已实现但前端无调用入口）、Excel导入 ❌（leads/import 返回"暂未实现"占位） |
| 2 | 批量导入前必须进行字段校验，错误行要明确提示第几行、哪个字段错误 | ✅ 已满足 | PostsBulkImportService.tryImportRow 逐行校验必填字段（账号/平台/作品类型），失败时 push { rowIndex, raw, message }，rowIndex 为 1-based 行号，message 明确指出哪个字段错误。客资侧 ImportsService.validate 同理 |
| 3 | 允许部分成功、部分失败；成功数据入库，失败数据导出为错误文件 | ⚠️ 部分满足 | 部分成功/部分失败 ✅（逐行 try-catch，成功入库不影响后续行）。失败数据导出为错误文件 ❌（failedRows 仅在 HTTP 响应中返回给前端展示，未生成可下载的错误文件；import_tasks.error_file_url 字段存在但始终为 null） |
| 4 | 批量导入后生成导入记录，主管端可查看是谁导入、导入多少条、成功多少条、失败多少条 | ⚠️ 部分满足 | 导入记录 ✅（persistTask 写入 import_tasks 表，含 userId/totalCount/successCount/failCount）。主管端查看 ❌（GET /api/imports/tasks 仅返回当前登录用户自己的记录，无 admin/owner 查看全员导入记录的接口；前端也无主管端导入记录查看页面） |

## 详细分析

### 1. Excel 模板导入未实现

- **作品侧**：`ImportsController` 仅有 `POST imports/posts/paste`（粘贴导入），无 Excel 上传端点。
- **客资侧**：`POST leads/import` 存在但返回 `{ ok: false, message: 'Excel 上传暂未实现' }`（imports.controller.ts:26-31）。`GET leads/import-template.xlsx` 实际返回的是 CSV 文本而非真正的 xlsx 文件。
- **前端**：批量导入对话框（renderPostBulkImportDialog）仅提供粘贴文本框 + 分隔符选择，无文件上传控件。

### 2. 失败数据无法导出为错误文件

- `import_tasks` 实体定义了 `error_file_url` 字段（import-task.entity.ts:29-30），但：
  - `PostsBulkImportService.persistTask` 未设置该字段（始终为 null）。
  - `ImportsService.finishTask` 接受 `errorFileUrl` 参数但调用方从未传入实际文件 URL。
  - 无任何代码将 failedRows 写入文件系统或生成可下载链接。
- 前端仅在对话框内以列表形式展示前 50 条失败明细（posts-monitor.js:819-833），无"下载错误文件"按钮。

### 3. 主管端无法查看全员导入记录

- `GET /api/imports/tasks` 和 `GET /api/import-tasks` 均以 `session.userId` 过滤，仅返回当前用户自己的导入任务。
- 无 admin/owner 专用的"查看所有人导入记录"接口。
- 前端无导入记录列表页面（主管端或员工端均无）。

### 4. 客资批量导入前端入口缺失

- 后端 `POST /api/leads/import-paste` 已实现完整的客资粘贴导入逻辑（含校验、去重、入库）。
- 但前端 `public/js/leads-monitor.js` 及其他前端文件中无任何调用该接口的 UI 入口（无"批量导入客资"按钮或对话框）。

# #8 手动刷新 - 代码核对报告

| 序号 | 需求项 | 判定 | 证据/缺失说明 |
|---|---|---|---|
| 1 | 作品列表每条作品增加"刷新数据"按钮 | ✅ 已满足 | posts-monitor.js:129 渲染 `<button class="ghost js-refresh-post-metrics">刷新指标</button>`，仅在 postUrl 存在时显示；app.js:746 绑定点击事件调用 handleRefreshPostMetricsClick |
| 2 | 作品看板顶部增加"批量刷新当前筛选作品"按钮 | ✅ 已满足 | posts-monitor.js:43 渲染 `<button id="batchRefreshFilteredPostsBtn">批量刷新当前筛选</button>`（仅 admin/owner 可见）；app.js:748 绑定事件调用 handleBatchRefreshFilteredPosts |
| 3 | 刷新内容包括：点赞数、评论数、收藏数、转发数、客资数 | ⚠️ 部分满足 | 点赞/评论/收藏 ✅（metricsFetcher.js 抓取 likes/comments/favorites）。转发数 ❌（metricsFetcher.js 不抓取 shares，PostsMetricsService.fetchMetricsFromUrl 返回值无 shares 字段）。客资数 ⚠️（saveMetricsHistory 中通过 SQL COUNT 查询 leads 并写入 history，但不是"刷新"客资数到 posts 表，仅作为历史快照记录） |
| 4 | 刷新时显示加载状态，避免重复点击 | ✅ 已满足 | 单条：handleRefreshPostMetricsClick 设置 button.disabled=true + textContent="刷新中…"（posts-monitor.js:755-757）。批量：batchRefreshFilteredPostsBtn 同样 disabled + "刷新中…"（posts-monitor.js:789-792） |
| 5 | 刷新失败时记录失败原因，可重试 | ⚠️ 部分满足 | 单条失败：前端 alert 显示 error.message（posts-monitor.js:768），按钮恢复可点击（可重试）✅。批量失败：后端 catch 块仅 push `{ id, success: false }`（posts.controller.ts:162），**未记录失败原因**（无 error.message 字段）；前端仅统计成功/失败数，无法展示具体哪条失败及原因 ❌ |
| 6 | 所有刷新结果写入 post_metrics_history，用于后续趋势查看 | ✅ 已满足 | 单条刷新：fetchMetrics 成功后调用 saveMetricsHistory（posts.controller.ts:138）。批量刷新：refreshMetrics 成功后同样调用 saveMetricsHistory（posts.controller.ts:159）。PostMetricsHistory 实体含 postId/likes/comments/favorites/shares/leadsCount/capturedAt 字段 |

## 详细分析

### 1. 转发数（shares）未被刷新抓取

- `metricsFetcher.js` 的 `scrapeXiaohongshu` 和 `scrapeDouyin` 函数均只返回 `likes`、`comments`、`favorites` 三个指标，无 `shares` 抓取逻辑。
- `PostsMetricsService.fetchMetricsFromUrl`（posts-metrics.service.ts:27-34）返回对象中无 `shares` 字段。
- `PostsService.updateMetrics`（posts.service.ts:232-240）虽然接受 `shares` 参数，但调用方从未传入该值。
- `saveMetricsHistory` 写入时 `shares` 始终为 0（因为 metrics 对象中无该字段）。

### 2. 批量刷新失败原因未记录

- `PostsController.refreshMetrics`（posts.controller.ts:161-162）的 catch 块：
  ```typescript
  } catch {
    results.push({ id: post.id, success: false });
  }
  ```
  未捕获 error 对象，未记录失败原因（如网络超时、页面结构变化等）。
- 前端 `handleBatchRefreshFilteredPosts` 收到的 results 数组中失败项仅有 `{ id, success: false }`，无法向用户展示具体失败原因。
- 失败原因也未写入数据库（post_metrics_history 无 error/status 字段）。

### 3. 客资数的"刷新"语义

- 需求要求"刷新客资数"，当前实现是在 `saveMetricsHistory` 中通过 `SELECT COUNT(*) FROM leads WHERE post_id = ?` 实时查询并写入历史快照的 `leadsCount` 字段。
- 这满足了"历史趋势记录"的需求，但 posts 表本身没有 `leads_count` 列，客资数是前端通过关联查询或子查询实时计算的，不存在"刷新到 posts 表"的动作。
- 从需求角度看，这个实现是合理的（客资数本身就是实时统计值，不需要"刷新"到 posts 表）。

# 总结

## #7 批量导入 - 关键缺失项

1. **Excel 模板导入**：作品和客资均未实现真正的 xlsx 文件上传解析
2. **失败数据导出为错误文件**：仅前端展示，无可下载文件生成
3. **主管端查看全员导入记录**：接口仅支持查看自己的记录
4. **客资批量导入前端入口**：后端已实现但前端无 UI

## #8 手动刷新 - 关键缺失项

1. **转发数（shares）**：Playwright 抓取器未实现转发数抓取
2. **批量刷新失败原因记录**：catch 块未捕获 error，无法追溯失败原因
