## 二、专项 B1：WebSocket 100+ 并发连接性能

> 依据 `运营中台四端口.md §11`："系统至少按 50-100 人同时在线设计"。

### TC-WSCC-001：100 个并发 socket 连接 CPU < 50%、内存 < 2GB

| 字段 | 内容 |
|------|------|
| **用例编号** | TC-WSCC-001 |
| **用例标题** | 100 个并发 socket 连接 CPU < 50%、内存 < 2GB |
| **关联需求** | §11 50-100 人同时在线 |
| **优先级** | P0 |
| **性能指标** | CPU 占用 < 50%（单核）/ 内存 < 2GB / 100 socket 连接平均握手 < 500ms |
| **关联源码** | `notifications.gateway.ts`（单实例 socket.io） |

**前置数据**：
- 100 个测试账号（sales_001 ~ sales_100）已创建
- 单台服务端（4C8G）

**测试步骤**：
1. 使用 `socket.io-client` + Node.js 脚本同时启动 100 个 socket 连接
2. 每个 socket 携带不同 token，握手加入 `user:UID` 房间
3. 持续 5 分钟不发业务事件
4. 监控服务端 `top` / `ps` 资源占用

**预期结果**：

| 检查点 | 预期值 | 验证方式 |
|--------|--------|----------|
| 连接成功率 | 100/100 | socket.on('connect') 回调计数 |
| CPU 占用 | < 50%（单核平均）/ 5 分钟内 P95 < 60% | top 命令 5 分钟采样 |
| 内存占用 | < 2GB（包括其他进程） | ps aux RSS |
| 握手延迟 | P50 < 200ms / P95 < 500ms / P99 < 1s | 客户端时间戳 |
| 连接保持 | 5 分钟内无自动断开 | socket.connected 持续 true |

**潜在缺陷**：socket.io 单进程房间数过多时内存增长非线性，100 个连接应 OK 但 1000+ 需考虑集群。

## 十二、执行建议

### 12.1 执行顺序

1. **优先 B10（TC-AUTF-001~010）**：登录是入口，先打通
2. **再跑 B1 + B6（WebSocket + 通知性能）**：依赖 100 并发 socket
3. **然后 B2 + B8 + B9（分页）**：列表性能
4. **B3 + B4（导入导出）**：异步任务
5. **B5（缓存）**：依赖 Redis 部署
6. **B7（账号矩阵）**：前端性能

### 12.2 工具建议

- **压测工具**：`wrk` / `ab` / `k6` / `locust`
- **socket 压测**：`socket.io-client` + `cluster` 模块
- **DB 监控**：`SHOW PROCESSLIST` / `EXPLAIN` / `slow_query_log`
- **Node.js 监控**：`clinic.js` / `0x` / `node --inspect`

### 12.3 压测基线配置

| 资源 | 推荐配置 |
|------|----------|
| 服务端 | 4C8G（生产环境 8C16G） |
| MySQL | 8C16G，独立部署 |
| Redis（若启用） | 2C4G |
| 客户端 | 1Gbps 内网 |

### 12.4 性能验收标准（P0 必须达标）

- 登录 < 2s ✓
- 列表分页 < 1.5s ✓
- 状态更新 < 1s ✓
- 消息推送 < 3s ✓
- 100 socket 并发 CPU < 50% ✓
- 1000 通知/秒 推送 P95 < 3s ✓
