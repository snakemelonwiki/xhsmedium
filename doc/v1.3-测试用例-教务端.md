# 教务端测试用例文档 - 我的成交

> 版本：v1.3 四端口迭代
> 适用端：教务端 `academic`
> 依据文档：`doc/v1.3-四端口迭代任务清单.md`（AC-1、SA-8、SA-9）
> 覆盖范围：教务端「我的成交」菜单、订单列表、订单详情、数据流转、权限隔离、搜索筛选

---

## 一、测试目标

教务端「我的成交」验收目标，是确认教务人员可以稳定查看和管理从销售端流转过来的已成交订单：

1. 能登录并进入教务端，侧边栏可见「我的成交」菜单。
2. 能查看已成交/已流转的订单列表，列表字段完整准确（订单编号、客户姓名、产品类型、服务类型、保障类型、付款阶段、成交金额、成交销售、负责教务、当前阶段、风险等级、订单状态）。
3. 能点击订单行进入订单详情，详情结构与 SA-8/SA-9 已建订单结构一致。
4. 能实时接收到销售端新创建的订单（Socket.IO 通知），教务端列表自动刷新。
5. **不能**看到未成交客资（deal_status != deal_done 的数据在教务端不可见）。
6. 搜索、筛选、分页、空状态等边界情况处理正确。

## 二、测试账号与基础数据

### 2.1 测试账号

| 角色 | 建议账号 | 用途 |
| --- | --- | --- |
| 教务 A | `academic_a` | 主测试账号，查看和管理流转订单 |
| 教务 B | `academic_b` | 权限隔离对照账号 |
| 销售 A | `sales_a` | 创建成交订单，触发数据流转到教务端 |
| 销售 B | `sales_b` | 辅助测试订单数据隔离 |

### 2.2 基础数据

| 数据 | 要求 |
| --- | --- |
| 已成交订单 | 至少 8 条，覆盖以下订单状态：待接收（to_receive）、跟进中（following）、已完成（completed）、已退款（refunded）；涉及多个销售；部分 assign 给教务 A，部分 assign 给教务 B |
| 未成交客资 | 至少 3 条 deal_status = not_deal / deal_pending，用于验证教务端不可见 |
| 同一客户多订单 | 同一客户名下至少 2 条订单，用于验证客户维度数据聚合 |
| 销售端成交订单 | 销售 A 通过 SA-8 录入至少 3 条成交记录，SA-9 流转到 orders 表 |

| AC-01-016 | P1 | 订单详情 — 产品/服务/保障类型展示 | 订单包含不同类型的产品、服务、保障 | 1. 进入各类型订单的详情页<br>2. 分别查看产品类型、服务类型、保障类型字段 | 类型字段以中文标签展示，而非后端原始枚举值；产品类型覆盖：专利、期刊论文、硕士毕业论文、博士毕业论文、基金、EI 会议、普刊、国际会议；服务类型覆盖：辅导、全流程、润色、返修、代投；保障类型覆盖：保录、保盲审、不保 | 类型值未知或为空时显示「未知」或「--」，不显示枚举 key |
| AC-01-017 | P2 | 订单列表导出 | 列表中至少存在 3 条订单 | 1. 点击列表页的「导出」按钮（如存在）<br>2. 选择导出范围（当前筛选/全部） | 触发导出任务；导出的 Excel/CSV 文件包含订单列表所有展示字段；只导出已移交订单，不导出未成交客资 | 大数据量时异步生成，不阻塞页面；导出完成后可下载 |
| AC-01-018 | P2 | 订单编号规则校验 | 通过销售端 SA-8 创建多条订单 | 1. 在同一天创建多条订单<br>2. 跨天后再次创建订单 | 同一天内订单编号格式为 `ORD-YYYYMMDD-00001`、`ORD-YYYYMMDD-00002` ... 自增无误；跨天后序号重置为 `ORD-YYYYMMDD-00001` | 并发创建时序号不重复（数据库唯一约束或 Redis 原子自增保证） |
