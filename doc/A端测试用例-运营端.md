# A端测试用例文档 - 运营端

> 版本：v1.2 完整交付版  
> 适用端：运营端 `operation`  
> 依据文档：`doc/运营中台四端口-当前问题.md`、`doc/运营中台四端口.md`、`doc/v1.2-完整交付版-AB端任务分配.md`  
> 覆盖范围：运营首页、排行榜、个人看板、作品录入、客资录入、客资看板、协同处理、我的作品、作品广场、账号管理、消息中心、导出中心、权限与性能稳定性。

## 一、测试目标

运营端验收目标不是只确认页面能打开，而是确认运营人员可以稳定完成每日核心工作：

1. 能登录并只进入运营端可见菜单。
2. 能快速录入作品，支持链接解析、手动兜底、封面/截图上传、去重、草稿与异常保留。
3. 能快速录入客资，支持粘贴解析、截图上传、绑定来源作品、分配销售、草稿恢复。
4. 能查看自己的作品、客资、排行榜、学习榜单、作品广场和个人看板。
5. 能处理销售发起的运营协同，并通过消息同步销售端。
6. 能按权限导出自己范围内的数据。
7. 长时间使用、重复提交、上传失败、Token 失效、WebSocket 断开等边界情况下不丢数据、不越权、不明显卡顿。

## 二、测试账号与基础数据

### 2.1 测试账号

| 角色 | 建议账号 | 用途 |
| --- | --- | --- |
| 运营 A | `operation_a` | 主测试账号，拥有账号、作品、客资、协同任务、消息、导出任务 |
| 运营 B | `operation_b` | 权限隔离对照账号 |
| 销售 A | `sales_a` | 接收运营 A 分配的客资，发起协同 |
| 主管 | `admin` 或 `owner` | 校验运营数据在主管端同步可见 |

### 2.2 基础数据

| 数据 | 要求 |
| --- | --- |
| 运营账号 | 至少 2 个归属运营 A，1 个归属运营 B；平台覆盖小红书、抖音 |
| 作品 | 运营 A 至少 25 条，其中获客数 `>=5` 的优秀作品不少于 3 条；运营 B 至少 5 条 |
| 客资 | 运营 A 至少 25 条，覆盖未分配、已分配、待添加、未通过、协同中、已通过、已成交、无效 |
| 协同任务 | 至少 1 条待运营处理、1 条已处理、1 条超时 |
| 消息 | 运营 A 至少有协同申请、客户未通过、销售添加成功、主管建议 4 类消息 |
| 导出任务 | 至少有 processing、completed、failed 三类状态 |

## 三、优先级说明

| 优先级 | 含义 |
| --- | --- |
| P0 | 不通过则不能交付；涉及登录、录入、权限、协同闭环、数据不丢失 |
| P1 | 影响核心使用效率；涉及筛选、分页、导出、消息跳转、统计口径 |
| P2 | 体验完善；涉及空状态、展示细节、排序、弱网提示 |

## 八、运营端验收通过标准

运营端交付前至少满足：

- P0 用例全部通过。
- P1 用例通过率不低于 95%，未通过项必须有明确上线风险说明。
- 不存在运营查看他人私密客资、导出越权、上传/刷新导致表单清空的问题。
- 作品录入、客资录入、协同处理、消息跳转、导出任务均至少完成一轮真实 MySQL + live NestJS 验收。
- 连续使用 1 小时不出现卡死、无法提交、必须刷新重进的问题。
