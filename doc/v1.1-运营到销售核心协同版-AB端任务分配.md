# 运营中台四端口 — 第2版：运营到销售核心协同版 A/B端任务分配

> 创建日期：2026-05-31  
> 依据文档：`doc/运营中台四端口.md`  
> 版本定位：在第1版基础上，补强“运营录入作品/客资 -> 分配销售 -> 销售跟进 -> 发起协同 -> 运营处理”的核心流程。  
> 适用范围：A/B 两人全栈开发派活、联调、测试验收。

---

## 一、版本目标

本版本只聚焦运营到销售之间的核心协同链路：

```text
运营录入作品/客资
-> 分配销售
-> 销售接收提醒
-> 销售查看客资并跟进
-> 销售发起运营协同
-> 运营处理协同
-> 销售收到处理结果并继续跟进
```

本版本必须达到：

- 运营端能录入作品、录入客资并分配销售。
- 销售端能接收分配客资、查看详情、更新添加/跟进状态。
- 销售能发起运营协同。
- 运营端能收到协同任务并处理。
- 销售端能收到运营处理结果提醒。
- 基础消息提醒、红点、未读数可用。
- 整条链路可测试、可回归。

## 五、A/B 共同修改文件与冲突边界

本版本虽然按 A/B 分工推进，但“客资、协同、通知、状态枚举、全局导航”属于共享区域，必须提前约定主责，避免两端同时修改同一段代码造成冲突。

## 5.1 高冲突文件

| 文件 | A/B 都会修改的原因 | 建议主责 |
| --- | --- | --- |
| `public/js/leads-monitor.js` | A 要改运营客资录入、运营客资看板、运营协同处理；B 要改销售我的客资、待跟进、销售协同、跟进操作。该文件当前同时承载运营/销售/主管客资相关视图。 | B 主责状态机和销售流程；A 只改运营录入/看板区块。 |
| `backend/src/modules/leads/leads.controller.ts` | A 要用 `POST /api/leads` 创建客资并分配销售；B 要用同一组接口做销售查询、状态更新、跟进、未通过、已添加。 | B 主责接口口径；A 按约定传字段。 |
| `backend/src/modules/leads/leads.service.ts` | 客资创建、筛选、销售权限、状态变更、通知触发都会落在这里。 | B 主责。 |

## 八、交付判断

本版交付时，不以页面数量作为唯一标准，而以核心链路是否跑通作为验收依据。

必须至少完成一条完整链路：

```text
运营录入作品
-> 运营录入客资并分配销售
-> 销售收到提醒
-> 销售跟进并申请协同
-> 运营收到协同并处理
-> 销售收到处理结果
-> 销售继续跟进并更新状态
```

只要这条链路可登录、可操作、可保存、可提醒、可回查，就可以视为第2版核心目标达成。
